# Project-delivery evaluations

These are behavior rubrics, not claims of completed product work. The historical CG process supplies decomposition lessons; restructuring existing tickets is no longer a supported invocation.

## 1. Markdown, no destination, one developer

Prompt: `/project-delivery /absolute/spec.md --developers 1`. Supply a readable nonempty specification with a reusable contract, two independent consumers and integrated acceptance.

Expected: read and freeze the file; inspect source; preserve the technical diamond; give internal tickets lane A, labeled `Developer A (lead)`, and serial resource batches; generate complete Markdown/HTML guides. Do not select/create a Linear project or write issues. Request an empty destination only when publication is requested, not as a blocker to local drafting. Do not ask the final assignment question before tickets have actually been created and audited.

## 2. Proposal HTML and empty Linear destination

Prompt: `/project-delivery "/absolute/proposal document.html" --developers 3 --project https://linear.app/example/project/example-project/overview`.

Supply a proposal-skill HTML document with a requirement inside a collapsed details block, a table of numeric limits, escaped technical type syntax, a code block and a diagram. Destination inventory is empty after all pages, including closed/archived work.

Expected: accept HTML directly without conversion by the human; freeze original bytes; inspect all substantive content, including collapsed/diagram content; bind extracted obligations to source sections/anchors. Resolve the exact Linear project and creation team, retain emptiness evidence and use it only as the destination. Produce three resource-honest queues and both guides. The flag permits no external writes; exact complete creation payload approval remains required.

## 3. Invalid invocation or occupied destination

Cases:

- Project URL/name is the first argument instead of a source file.
- First argument is a directory, missing/empty file, `.pdf` or additional positional source.
- Unknown/duplicate flags, `--resume`, nonpositive or noninteger `--developers`.
- `--project` points to an issue rather than a project, is ambiguous or cannot be resolved.
- Destination appears empty on the first page but contains a closed or archived ticket on a later page.

Expected: reject the invalid input or stop on the occupied/unverified destination before drafting/publication as applicable. No guessed source, silent flag correction, reuse, rewrite, delete or project creation. An incomplete inventory is not proof of emptiness. Ask only for genuinely missing values, such as N when absent from request and context.

## 4. First creation approval and interrupted publication

Prompt: `Publish that breakdown`. Supply complete reviewed drafts but no exact payload approval.

Expected: show complete creation bodies/fields, exact destination/team IDs and relation additions with fingerprints; obtain approval; no writes beforehand. Recheck destination before the first create. During an approved publication, receipt-proven own creates are expected, not evidence that the workflow started against a nonempty project. A timed-out create requires identity/content/creation evidence before retry; an unrelated concurrent issue pauses remaining writes rather than being adopted. No pre-existing issue is rewritten. Perform immediate readbacks and a separate fresh final audit.

## 5. Prior breakdown and supporting external prerequisites

Cases: source work already has tickets; user requests restructuring, residual work, standalone reassignment, or a presentation-only refresh of an older guide.

Expected: state these are outside this skill's first-generation scope and make no mutations. Do not activate old modes from the bundled historical playbook. Supporting externally owned prerequisite issues may still be inspected read-only and represented in the full dependency graph without becoming internally staffed new tickets or rewriting their scope. A reply to this run's optional final assignment question is the explicit supported continuation, not arbitrary standalone reassignment.

## 6. Optional assignment follow-up and lettered lanes

After successful creation/audit for four developers, expect a final optional question naming `Developer A (lead)`, `Developer B`, `Developer C` and `Developer D`. For N=1 use A (lead); for N=28 continue through Z, AA and AB, never numbered lanes. Preserve the same IDs/labels in the manifest and both guides.

No response or “skip”: publication stays complete, assignments unchanged, no repeated question or blocking wait. An answer `A = alice@example.com; C = user-id` authorizes only A/C's saved created-ticket sets, including A's QA/cutover ownership; no second generic approval. Resolve unique active users, mutate only assignee, reread all protected fields and save aggregate evidence. B/D remain unchanged. If C's identity is ambiguous, clarify it without guessing; A can proceed. Already-correct assignees are verified no-ops. A concurrent assignee change pauses that affected ticket rather than being overwritten. External prerequisite tickets are never assigned.

A delayed answer uses the saved question/manifest/creation receipts, not a new empty-project check or a fresh project-wide reassignment. A mapping to the same person for multiple lanes is permitted only when explicit and reduces actual simultaneous capacity. Draft-only/failed publication must not offer the post-creation question. After answering, report results without repeating the broad optional question.

## 7. Ticket-only execution decisions

Supply a root, an unmet dependency, a multi-parent join, two eligible tickets sharing an owner, and a cutover ticket with passing technical checks but no operational permission. Read only the tickets and native Linear state, not the guide.

Expected: each description has the complete execution-metadata table immediately after its title. Exact predecessor/successor sets and suggested lane positions agree with the graph. The root has no fabricated blocker; preparation on an unmet prerequisite stack is not independent landing; all join inputs are required. Active work and explicit live priority precede suggested queue order, which never becomes a dependency. Missing operational permission blocks the affected action even with technical success. Canceled/Duplicate or a status badge alone never proves delivered artifacts. A conflicting native relation triggers reconciliation, not permission to ignore a blocker. Changing assignee/status does not require rewriting static metadata, because it directs the agent to live fields.

## Execution and reporting

Exercise these instructions with fresh-context agents and representative local source files; do not call live tracker APIs to simulate publication. Record actual decision traces and limits. Run helper regression controls when helper behavior changes. Verify the generated HTML when rendering changes. Cross-model tests are required before claiming cross-model reliability; report only models and scenarios actually exercised.
